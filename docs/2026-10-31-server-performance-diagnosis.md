# 2026-10-31 第四轮测试：中心服务端性能诊断与修复方案

> 后续状态：2026-11-01 已按此诊断实施修复，具体改动和验证结果见 [实施记录](plans/2026-11-01-server-performance-fix.md)。下文保留修复前的诊断依据。

结论：本轮最明确的持续性性能问题是**环境快照反复全量构建**；最有证据支持的触发源是玩家存档等动态文件更新。中心服的世界 tick 挂起和出生点预热禁用已生效；修复应优先处理环境同步的数据分类和构建方式。另有主线程元数据持久化、玩家存档重复压缩等次要开销。

这是日志、源码和隔离探针共同支持的诊断。日志未记录具体触发路径或清单差异，玩家数据是高置信触发源，不能逐轮断言全部 95 次构建均由它触发。没有服务器 CPU/JFR、磁盘吞吐或 GC 采样，因此不能给出各项资源占比，也不能保证修复后下降某个百分比。本次提供分析和修复方案，未修改模组实现。

## 触发链

1. `GroupServerHooks.java:190` 每 20 tick 采集玩家完整 NBT，交给玩家数据上传器。上传器已有相同内容去重；游戏过程中内容会持续变化。
2. `PlayerDataHandlers.java:81` 在后台写入真实存档的 `playerdata/<uuid>.dat`；`PlayerDataFileStore.java:75` 完成校验、写临时文件、刷盘及原子替换。
3. `EnvironmentPathPolicy.java:21` 的内置排除表没有 `world/playerdata`，`P2PServerService.java:494` 对实际存档路径生成的排除表也没有这一项。临时 `.p2p-tmp` 被排除，最终 `.dat` 仍属于环境文件。
4. `EnvironmentSnapshotManager.java:369` 的文件监视器把最终玩家文件替换识别为环境变更，启动构建。
5. `EnvironmentSnapshotStore.java:72` 每次遍历全部入选文件，逐个调用 `materializeStableBlob`。`:319` 先完整复制并计算 SHA-256，`:329` 才检查内容 Blob 是否已存在。因此内容去重只节省最终持久存储，不能避免重新读取、哈希和临时写入。
6. `EnvironmentSnapshotManager.java:278` 构建前后各算一次目录指纹；构建期间继续发生玩家保存时，dirty 标记会使下一轮立即启动（`:307`）。当前实现还会完整构建同一个 ID，再打印发布日志。

按当前实现，95 轮、每轮 71 文件至少对应 **6745 次完整文件复制与哈希处理**；实际字节数取决于那 71 个文件的大小，日志未提供。每轮另有两次目录指纹遍历。

还有一个放大因素：`EnvironmentSnapshotStore.java:294` 和 `EnvironmentSnapshotManager.java:446` 使用 `Files.walk` 后再过滤，排除的 `player-to-player`、世界数据等目录仍会被递归枚举，只是不进入清单或注册监听。目录规模增长后，遍历也会变贵。

不能把 95 次构建等同于 95 次全量网络下载：`EnvironmentRuntimeIdentity.java:30` 已把普通世界数据排除在启动环境哈希之外，`EnvironmentUpdateServer.java:79` 按该哈希抑制通知。当前缺口主要是**实际快照构建规则没有与静态环境身份规则统一**。

## 最小复现

隔离探针位于 `build/tmp/env-perf-probe/`，使用当前真实路径策略与快照存储类重新编译运行；人工创建一个不变的 1 MiB 模组文件，以及 playerdata、stats、advancements 三个文件，不使用真实世界。

- 只修改玩家 `.dat`：环境快照 ID 变化。
- 用文件监视器观察临时仓库：这一轮仍创建 4 个 staging 文件，不变的模组也被重新复制。
- 不修改任何源文件，再调用一次构建：快照 ID 相同，仍创建 4 个 staging 文件。
- 将三个动态目录加入额外排除表后：清单只剩模组文件；再改玩家 `.dat`，快照 ID 保持不变。

探针进程退出码为 0，证明了错误分类和全量重复制机制。源码用 `javac --release 17` 编译，本机 Java 21 运行，依赖现有 Gson 2.10.1、SLF4J API 2.0.7；命令和输出分别保存在 `build/tmp/env-perf-probe/run.ps1`、`result.txt`。它不是部署环境的性能基准，不证明真实 CPU 占比；排除 stats/advancements 的实验也不代表其跨节点持久化已经完备。

## 修复顺序

### 第一优先：切断玩家存档到环境构建的触发

在中心、下载端、中转端统一按实际存档路径排除 `playerdata/`，包括 `.dat` 和备份。玩家状态继续通过现有专用上传、下载、退出最终快照通道传输。需要覆盖自定义 `level-name`，不能只硬编码 `world/`。

临时部署验证可在中心 `player-to-player/config.json` 的 **现有** `nonEnvironmentPaths` 数组中追加 `"world/playerdata"`，然后重启。此次日志的世界目录是 `world`；其他部署使用真实世界目录。此配置只是停止将玩家文件视为环境，不删除玩家文件，也不停止其专用同步。本次没有修改部署配置。

stats、advancements、世界持久状态和模组自定义维度也应与启动环境分离，但需先核对各自的数据传输和恢复覆盖，补齐缺口再迁移。不能直接排除整个世界目录：数据包和 `serverconfig` 等启动资源仍需同步，也不能把未实现的数据通道当作已经存在。

### 第二优先：让环境重建与实际变化量成正比

- 记录具体 dirty 路径；未变化文件复用已有清单条目与不可变 Blob。变化文件仍需稳定读取、SHA-256 校验和原子发布，不能仅凭大小相同认定内容相同。
- 正确处理监听溢出、漏事件和文件删除重建；保留周期校验兜底。源状态不确定时扩大重新校验范围，必要时全量校验，避免永久复用陈旧条目。
- 目录遍历改为进入目录前判断是否跳过整棵子树，避免反复走进已排除的存档、日志、快照仓库。
- 保留单构建任务机制，对构建期间的事件合并并设置合理的最短重建间隔和最大延迟，避免立即重建循环，也避免持续变化时永远不发布。
- 同内容构建不作为新版本发布；这是补充优化，核心仍是阻止重复制，不能只消除日志。
- 历史无效清单一次性分类隔离并汇总告警，后续按引用关系回收失效资源，避免每次启动重复处理 280 份旧清单。

上述环境改动通常不需要新增消息类型，但会让包含动态文件的旧快照失效，需明确升级行为并验证中心、中转和客户端下载规则一致。

### 第三优先：降低同步持久化的主线程及磁盘开销

- `MetadataService.java:362` 每秒在主线程采集元数据；`MetadataStore.java:265` 在同一调用路径压缩完整检查点并 `force(true)`。应在主线程生成不可变采样，交给串行后台持久化器，完成后再推进可发布版本。自然时钟采样可合并，离散命令、任期和切换屏障保持顺序及耐久确认。
- `PlayerDataFileStore.java:75` 每次先解压校验再重新压缩，还对临时文件和目标文件分别 force。先考虑校验后保存已收到的压缩字节；多人扩展时可用玩家数据批量 WAL 加后台文件物化。现有去重和序号屏障继续保留，退出最终数据必须等待耐久确认。
- 不能通过取消刷盘或提前 ACK 获得性能数字；那会破坏已经承诺的断线恢复与退出保存语义。
- 中心服登录阶段仍可能加载或生成玩家周边区块，本轮约 15 秒。长期可把登录改为轻量接入流程，减少真实世界视距票据；它不是当前两分钟环境重建风暴的首要修复项。

## 验收

1. 无模组/配置变化，单人连续移动、挖掘 5 分钟：玩家存档继续确认，环境快照版本不再随之变化，也不持续执行全量构建。
2. 修改一个受同步管理的配置：合并事件后发布正确版本；模组大文件未变化时不重复复制；断开和重新连接后仍能应用更新。
3. 覆盖自定义存档目录、中转、两玩家、跨组切换、退出重进，确认玩家位置及背包恢复正常。
4. 以相同负载采样修复前后的进程 CPU、磁盘读写、MSPT/GC；增加环境构建耗时/字节数/触发路径、元数据检查点耗时和玩家持久化耗时指标。
5. 实施后运行 Gradle 测试与 build，并完成上述客户端/中心服角色冒烟。本文阶段未修改生产代码，因此未将完整构建或实机性能改善作为已完成结果。
