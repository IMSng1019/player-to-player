# 2026-11-01 联机反馈修复与验收

依据：`player_to_player-prompt.txt`、`test_log/26.11.1`，以及本地 Minecraft 1.20.4 字节码与回归测试。

## 修复内容

### 准备组客户端耗时

日志中两次主客户端指派到切离物理服约为 15 秒和 14 秒。提供的客户端日志止于环境自动重启，无法据此进一步拆分计算进程启动耗时。

运行环境原来每次重新安装，丢弃本机 Fabric 的 remappedJars / processedMods。现在仅在环境运行哈希与 Java 运行时一致、上次计算进程已经完整就绪时复用这两类本地缓存；失败或取消的启动、变更环境仍冷启动。源文件照常重新安装，文件哈希、权限、元数据和 READY 校验保持有效。缓存以独立文件复制，不与上一实例共享可写文件。

新增运行环境安装、文件验证、模组/数据包加载、状态确认阶段提示，以及 `worker_start` 阶段计时。首次进入新环境仍有 JVM 冷启动成本；未测量真实用户电脑上的优化后秒数，不宣称固定降幅。

### 跨组玩家名补全与正版皮肤

- 经 `PERMISSION_RELAY` 同步全局在线名字目录，补入原版客户端与计算服务端的玩家名候选。玩家退出或切换服务器后清理相应目录，不创建虚假玩家实体。
- 原先放在客户端 Mixin 列表中的玩家指令路由拦截移入公共列表，使独立计算服务端实际执行跨组指令路由。
- 物理服原版登录取得的 GameProfile 属性（含 textures 值与签名）经组权限资料、父子 IPC、一次性 TCP 端口授权传给计算服务端的原版登录流程。
- 新主及副端均等待匹配本组的身份资料，避免角色切换后使用旧组资料或空皮肤提前登录。皮肤下载及签名校验继续由原版客户端完成。

### 主客户端退出后继续游戏

原流程直接停止计算进程，同组副端的普通断线回调会拆除控制会话；退出数据完成保存时，服务端已将副端视为离线，随后解散旧组。

新流程先固定退出保护，向仍在线成员请求交接准备；成员完成编排性断开旧游戏连接、保留控制会话后回复 ACK。全部必要确认完成才允许旧主停服。最终数据应用并耐久释放旧所有权后，按剩余成员算力选主，准备权威存档并启动新计算进程，组就绪后再连接跟随成员。重复请求、未确认、保存失败重试和真正离开的成员分别处理，不重复改组。

这条修复沿用当前仓库的“保存后启动后继计算进程”能力，交接期间显示等待界面；没有实现提示词设想的所有副端完整热备与 300ms 内无感切换。强杀、断电等非正常退出也不等价于本次正常退出交接。

## 兼容性与尚需现场复测

`Protocol.VERSION`、消息编号与 `fabric.mod.json` 未变；`PERMISSION_RELAY` 增加字段，`SPLIT_PREPARE` 增加 `reason=primary_exit` 及同事务确认语义。公共/客户端 Mixin 清单有变化。服务端、主客户端、副客户端应统一更新到本次构建，旧客户端不会回复退出交接确认。

没有使用真实账号或两台远程图形客户端执行联机复测；皮肤纹理最终下载、实际渲染、跨公网 P2P/中转以及主端退出后各成员位置和背包的连续性，仍需现场双端验证。自动化验证覆盖实际登录属性传输，不替代原版客户端向纹理服务器下载图片。
