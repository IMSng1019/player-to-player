# 环境同步与独立计算进程

本实现使用协议 **8**。中心服务端、中转端和玩家客户端需要统一升级；协议 7 节点不能混连。新增登录阶段查询、只读环境控制会话、环境更新消息、父子进程本机消息，以及客户端连接/子服务端登录 Mixin 和启动前环境记录入口。

## 进入服务器

1. 普通服务器按原版连接；P2P 服务器在 Fabric 登录协商阶段公布真实控制端口、服务实例标识、存档实际相对路径和环境版本。
2. 需要准备环境时，客户端主动结束本次游戏登录，在独立控制连接上下载，不占用原版登录超时窗口。该连接不能登记玩家、申请区块或上传状态。
3. 主副两套环境从同一个不可变快照下载，先写暂存目录，再校验整个文件集和摘要。服务端已删除的文件不会遗留在新目录。安装有恢复日志，失败或取消不会把半套新环境当作成功。
4. 实际客户端模组和启动配置需要符合服务器要求。模组增删改、启动配置变化或首次切换独立运行目录时，生成该服务器专属游戏目录并自动重启；环境匹配时直接继续登录。原游戏目录的 mods/config 不被覆盖，主计算进程和渲染进程继续分别加载主副两套角色环境。
5. 预检成功后重新连接，正式 HELLO 才创建玩家会话。环境准备票据绑定连接目标、服务实例及运行环境版本，取消/切服使旧票据失效。

## 自动重启与失败恢复

重启顺序为：**下载并校验 → 安装独立目录 → 辅助进程就绪 → 再次检查连接目标及取消状态 → 提交重启 → 正常退出旧游戏 → 启动新游戏 → QuickPlay 回服**。

辅助进程仅依赖 JDK，固定使用 16 MiB 初始堆、64 MiB 最大堆，不继承游戏的大内存设置。
完整启动参数通过匿名进程管道传入，不写参数文件、重启状态或辅助进程日志。
每次重试都重新读取当前登录身份，保留认证 agent 和所需的 JVM 参数。新游戏从安装目录
读取 mods；旧 `fabric.modsFolder`、额外模组目录和旧 QuickPlay 目标不会继续生效。
参数直接交给 Java 进程，不执行服务器提供的启动脚本。Windows 参数按 Java 启动器的规则
单独编码，保留中文、空格、反斜线与字面双引号；参照
[OpenJDK Windows ProcessImpl](https://github.com/openjdk/jdk17u/blob/master/src/java.base/windows/classes/java/lang/ProcessImpl.java)。

准备握手及提交确认各限时 10 秒，失败会停止本次辅助进程并保留原客户端。收到就绪确认后，
客户端在主线程再次核验连接代次、目标及当前界面，然后锁定取消/重复连接操作。
只有提交确认成功才调用正常退出入口，沿用现有存档和退出屏障。辅助进程一直等待旧 JVM
在操作系统中实际结束，没有强制退出期限，也不会强杀游戏。

同一服务器的连续自动连接链最多自动重启一次，服务端再次更新版本也不重置预算。
重启后仍不匹配时，界面保留具体环境差异并提供手动重试；取消后重连同一地址也不会自行
反复重启。主动连接其他服务器会建立新的连接链。自动触发与手动重试共用同一个协调器。

本机任务位于共享数据根的 `client-restarts/<任务UUID>.properties`，记录连接链、目标地址、
环境版本、安装目录、进程身份、阶段及固定失败代码，不记录账号、认证参数或启动命令。
读写共享跨进程锁，文件先写临时副本并刷盘，再原子替换，避免 Windows 读句柄阻碍重命名。
新客户端在 Fabric `CLIENT_STARTED` 事件中回报；该事件表示客户端运行循环即将开始，
**不等于资源加载完成或已成功进入服务器**。提前退出记录失败；5 分钟未收到回报则记录
“初始化未确认”，保留仍在加载的游戏。晚到的合法回报仍可确认成功。

下次打开主菜单时会展示没有相关存活进程的未完成任务，可打开安装目录或使用当前账号
重新连接、校验并重试；仍在加载的实例不会出现重复启动入口。开发环境，以及主入口不是
可还原的 Fabric KnotClient 的包装启动器，保留手动启动说明。此版本不负责升级本机 Java、
Minecraft 或 Fabric Loader，仍要求基础运行时与服务端兼容。

## 主客户端如何计算世界

玩家电脑后台启动一个独立的 Fabric 专用服务端 JVM，使用已校验的主角色模组和配置。服务端专用模组可以按其原有物理 SERVER 环境加载。父进程继续负责游戏界面、中心控制连接和 P2P；子进程通过认证回环通道使用现有区块申请、上传、合并分离和退出持久化链路。

发行环境需要环境根目录包含一个可识别的 Fabric 服务端启动 JAR 及其依赖。按 JAR 清单的官方 Fabric 启动入口识别，支持 `fabric-server-launch.jar`、官方带版本号的下载包以及管理员重命名的启动包；多个候选会明确报错，不会任选旧版本，也不扫描 `.fabric/server` 缓存来猜测入口。只直接执行本机 Java 与该启动 JAR，不执行环境附带的 bat/sh。开发环境通过 `writeWorkerLaunchSpec` 导出本机 Loom 的真实 server 启动配置，`runClient` 自动传入该描述。

子进程只监听回环地址，游戏连接必须先由父进程登记经过认证的玩家身份。未登记的本机直接连接也会被拒绝。父子握手绑定随机令牌与实例代次；READY 需匹配环境清单和运行版本，并验证实际加载的服务端模组。

实际存档与运行目录分离。世界身份一致时保留已有世界状态，但在启动前重新应用 `datapacks/` 与 `serverconfig/`，包括删除项；不得借环境更新覆盖 level.dat、玩家、区块或模组 SavedData。

退出保留已有耐久屏障：准备退出 → 中心确认退出保护 → 子进程停服保存 → 最终载荷耐久提交 → 关闭会话。父进程确认操作系统中的子 JVM 实际退出后才允许重用目录，避免快速重连时两个实例同时写同一世界。

## 在线更新与回传

中心环境变化后通知在线客户端，另有周期查询补偿漏掉的通知。客户端将新版本下载到 `pending-environment/`，正在运行的实例继续使用自己的启动版本。模组和启动配置通过重新连接/重启应用，不尝试运行中热插拔。

组的运行版本在服务端记录。新旧版本不得加入同一个组或相互合并；旧版本组仍运行时，新版本角色申请会明确被拒绝。先让旧组完成退出，再启动新版本；更换中心服务端自身已加载模组时同样需要重启中心服务端。

主客户端默认可以回传 `config/` 下的修改。配置项：

- `environmentUploadPaths`：允许回传的相对路径树，默认 `["config"]`。可明确加入实际存档下的 `serverconfig/` 等环境资源路径；它们映射到实际存档目录，不能把运行目录中缺少该树误判成删除。
- `environmentUploadMaxBytes`：单文件上传限制，默认 8 MiB，协议侧上限同为 8 MiB。超过上限的文件由管理员发布。

上传携带文件的基础 SHA-256（空值表示原来不存在）。服务端仅接受当前主客户端会话，并在磁盘文件仍匹配基础版本时提交。冲突保留本地修改并提示；不会按最后到达顺序覆盖其他组或管理员的更改。重试提交同一内容不会重复变更。可执行文件、物理服务端管理配置和动态世界状态不能通过此通道回传。停服完成后另做一次有界配置收尾上传。

服务端的网络监听、RCON、认证设置和管理凭据不原样下发。影响演算的游戏设置使用共享白名单导出；子进程的监听和认证由本机宿主管理。
