- **这一条请你在游戏内确认**（下轮复测时用 F3 看那条带的地形）：是几格台阶，还是有真的空洞/断崖。它是"高低落差"定量归因的最后一个缺口，标 **[待实测]**。

## 3. 为什么没被自动隔离（不是代码 bug，是设计取舍 + 没做手工止血）

`quarantineStaleWorldState`（`P2PServerService.java:492-546`）的分支：

| 情形 | 行为 |
|------|------|
| 有标记且身份变化 | 自动隔离四个目录（`:521-540`）——**本次没走到这一支** |
| **标记缺失**（功能上线前的老部署） | **只 WARN，不隔离**（`:500-506`）——本次走的是这一支 |
| 身份哈希不同但种子相同 | 只 WARN（不隔离）——"同种子重建世界"是永久盲区 |
| 标记口径版本不同 / 身份取不到 | 只 WARN |

- server.log:65 的那条 WARN 就是"标记缺失"分支。注意 `hasAnyRuntimeState()` 只看**四个目录是否存在**（`:575-580`），所以**这条 WARN 不能证明旧数据还在**；真正证明"旧区块确实被下发"的是 §1 的磁盘比对。
- 但反过来说：既然客户端拿到了旧世界的区块字节，**服务端当时一定有旧载荷可发**——在"世界 region 已随 `world/` 删除"的前提下，载荷只能来自 `player-to-player/` 那四个目录，也就是 **`chunk-journal`（WAL payload）当时没有隔离**。
- ⚠️ **需要你确认**：在服务端上 `ls -la player-to-player/`，看有没有 `chunk-journal.stale-*` / `registry.stale-*` 之类的改名产物。若四个目录都改名过，则我的根因判断有误，请把清单给我，我重新溯源（否证条件见 §9）。
- **为什么这次（§1.5）就没事**：本次换世界时**标记已经存在**（10/14 23:13:46 那次启动写下的 a24255a5），新世界身份 9368c3a1 与它不符 → 走 `!sameWorld` 分支**自动隔离**四个目录（`P2PServerService.java:521-540`，日志形态是 `已隔离: {} → {}`）。而 10/14 那次是本功能上线后的**第一次启动**、标记缺失 → 只 WARN 不隔离 —— 事故正好落在自动隔离唯一覆盖不到的那个窗口里。
- 另外："区块注册表已恢复 0 条占用记录"（server.log:67）**不能**当作"隔离做过"的证据——组解散本身也会清掉占用。

- 客户端聊天反复出现原版文案"你没有权限打开游戏模式切换器"（client.log:139-142、208-212）——**本地集成服务端视角的权限等级 < 2**。
- **更正一处易误读的地方**：server.log:351-352 的 `Unknown game mode: LXW1019` 与 :382 的 `Nothing changed` 更像是**你在物理服务端控制台/面板里敲的**（`/gamemode LXW1019 1` 参数顺序写错；`/op` 重复执行），**不是**从客户端上送过去的。判据：`CommandChatHandlers.java:103` 对每一条上送指令都会打 `指令上送: 玩家 …` 的 INFO，而本次（和上一轮 `26.10.14`）服务端日志里 **"指令上送" 出现 0 次**——本次会话客户端**从未成功上送过任何指令**。

**代码事实（已用 javap 对 mojmap 1.20.4 核对原版链路）**：
- 本地世界的权限来自**本地世界自己**，而它被三件事同时压到 0：
  1. `GroupHost.java:183-184`：组宿主发布 LAN 时调 `publishServer(getDefaultGameType(), **false**, port)`——第二个参数是 `cheats=false` → 原版 `PlayerList.setAllowCheatsForAllPlayers(false)`；
  2. 环境骨架 `level.dat` 的 `allowCommands=0`（服务端建世界时的默认）→ `isSingleplayerOwner && worldData.getAllowCommands()` 这一支也不成立；
  3. 客户端目录里没有 `ops.json`（全盘 find 为空），且 `ops.json` 被环境策略明确排除（`EnvironmentPathPolicy.java:31`）。
- 原版落地链路（javap 核实）：`IntegratedServer.publishServer` → `setPermissionLevel(getProfilePermissions(profile))` → 权限 0 → `ClientboundEntityEventPacket(24+0)` → `LocalPlayer.permissionLevel = 0` → F3+F4 处 `Minecraft.player.hasPermissions(2)` 为 false → 直接显示 `debug.gamemodes.error`（就是那句"你没有权限打开游戏模式切换器"）。**客户端连指令都没发出去**，所以 `CommandsMixin` 的失败探针不会被触发（这也解释了"指令上送"为何 0 次）。
- **这条链路从来没有实现过**：`git log -S setPermissionLevel` 全史为空；`CommandRelayClient`/`CommandChatHandlers`/`CommandsMixin` 最后一次改动是 `da9a0ba`(0.0.9.8, 2026-07-12)，最近 5 个提交都没碰它 → **不是回归，是缺口**。
- 中继链路也救不了：中继的语义是"上送 → 服务端/其他组主客户端**代执行** → 回 message 或 action=teleport"（DESIGN §13.2、`CommandChatHandlers.java:149-150`），**代执行发生在别的世界里，改不了你本地这个世界的状态**（只有 `/tp` 特例与消息回传有本地效果）；而且只有一个组时泛化下放必然 `replyUnhandled`（`:191-193/199-201`）。
- 规范（`AGENTS.md:80`）说"单个组服务端相当于一个小服务器……只有全局性的指令和跨区块的指令需要分级下放"——本地指令本就该在本地执行；但规范**没有写**"服务端的 op 应让客户端本地也获得权限"，所以这属于**需要你拍板的口径缺口**，不是明确的规格违反。

**为什么"之前似乎可以下传"**（[已核实] 范围内的解释）：旧世界是**创造模式**（旧 level.dat `GameType=1`），你可以直接飞着看区块布局，根本不需要 OP；新世界是生存（`GameType=0`），本地权限缺口第一次暴露。本轮与上一轮日志里都**没有任何权限报错**、也没有任何上送记录；5 份历史会话日志里也没有任何"权限下传成功/中继代执行"的痕迹。

**结论**：`本地权限 ❌（三条判据全 false） / 上送链路 未触发 / 中继语义 不解决本地状态`——三者叠加成你看到的现象。

**复测里的新证据（同一条结论）**：`test_log/26.10.15/server/latest (3).log:152 [00:18:58]` 又一次 `Nothing changed. The player already is an operator` —— 这是**物理服务端自己的 ops 名单**在回答你，而客户端那一侧依旧 00:19:04-05 报"你没有权限打开游戏模式切换器"。**两句话说的是两个不同的服务端**：物理服务端的名单里你是 op，但你实际游玩的世界是客户端自己的集成服务端，它的名单（以及 `allowCommands`）里你不是。中间**没有任何通道**把前者搬到后者——这正是 §8 P1-B 要补的东西。

## 7.5 复测新增现象："我还在线，服务端却报我离开"

**现象**：人物还在玩，物理服务端却 `lost connection: Timed out` + `left the game`。

**机制（[已核实]，新日志时间戳逐条对齐）**：

| 事件 | 时间戳 |
|---|---|
| 进服 / 握手 / 角色指派 | 00:18:10 / 00:18:11 / 00:18:12 |
| 客户端"编排性断开物理服务端"切到本地组世界 | 00:18:12 前后 |
| **物理端 `lost connection: Timed out` + `left the game`** | **00:18:41（恰 +30 秒）** |
| 第二次同样的三段 | 00:20:27 / 00:20:28 / **00:20:57（恰 +30 秒）** |

这是**设计路径 + 原版超时**的组合：主客户端一旦接管世界就**不再应答物理连接的 keepalive**（客户端只是"弃用"这条连接，没有主动关闭），原版服务端等 30 秒无应答 → 判定超时踢人并打日志。**它不是新问题**（`test_log/26.10.14_2` 里同样是 +30s/+31s），只是这次你盯着看才发现。

**影响面（都是"没有影响"）**：
- **玩家表不受影响**：`players.remove(peerId)` 挂在 **P2P 控制连接**的断开路径上（`P2PServerService.java:361`，`HelloHandler.unregisterIfCurrent` 回调），不是 MC 连接。控制连接在切换后**继续存活**（1Hz 位置上报照常，`RegistryHandlers.java:342 players.updatePosition`）→ `/list`、跨组 `/tp`、`/msg` 依赖的玩家表照常刷新。
- **组与区块占用不受影响**：组的解散走退出事务（离线才解散），

**建议（P2，低风险，需你点头）**：让客户端在"编排性断开"时**主动关闭**这条连接（或在服务端识别切换原因后打更准确的日志），把"Timed out / left the game"换成一次干净断开。收益：物理端日志不再误导、幽灵 `ServerPlayer` 不再多留 30 秒。代价：要确认主动关闭不会破坏切换旗标与 `WorldSession` 的会话保持判定（`WorldSwitcher.SWITCHING` 一次性消费语义）。
