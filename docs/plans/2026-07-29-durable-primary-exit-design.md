# 主客户端坐标恢复与耐久退出设计

## 背景与根因

2026-07-29 的实测日志证明了两个相互独立的问题。

第一，物理服务端在两次登录时都正确恢复玩家位置
`(-107.04178617898495, 116.0, 10.831364490039894)`，并在切换前下发了在线玩家
NBT；主客户端本地集成服却两次都在打印 `Not a string` 后，以 `(0, 0, 0)` 创建
单人世界所有者。Minecraft 1.20.4 的 `PlayerList.load` 会优先读取
`WorldData.getLoadedPlayerTag()`，只要该值非 null 就不会读取
`playerdata/<UUID>.dat`。当前实现删除 `level.dat/Data.Player` 的做法不能保证加载结果为
null，因而错误的内嵌玩家状态仍覆盖了正确 UUID 文件。

第二，主客户端退出时没有上传最终玩家 NBT；停服产生的数千个
`CHUNK_RELEASE` 请求尚未收到确认，控制连接就被关闭。物理服务端先按断线释放整组，随后
到达的区块释放全部因所有权已消失而失败，造成位置、背包和区块尾部状态丢失。

## 已批准语义

- 首次加入物理服务器时使用物理服生成的出生状态；之后加入使用上一次成功持久化的退出状态。
- 主客户端正常退出世界或关闭窗口时，必须无限期等待，直到物理服务端恢复连接、接收全部最终数据、完成刷盘并确认事务提交。
- 不设置自动放弃超时。网络或物理服务端长时间不可用时，客户端保持运行并持续重试。
- 任务管理器强杀、操作系统结束进程、断电和 JVM 崩溃无法由模组拦截。此时物理服务端保留最后一次已经确认的实时玩家和区块数据。
- 如果客户端已取得退出意图确认后又被强杀，服务端先保留事务和区块所有权；同一客户端
  下次正常加入时，以最后实时确认数据耐久结束旧事务并释放占用。

## 坐标与玩家状态恢复

主客户端启动本地世界前，从物理服取得并校验权威玩家 NBT，然后原子安装到三个位置：

1. `playerdata/<UUID>.dat`
2. `level.dat/Data.Player`
3. 存在时的 `level.dat_old/Data.Player`

三个位置写入同一份权威 CompoundTag 的副本。所有临时文件先成功生成，再替换目标文件；
任何解析或写入失败都取消主客户端切换。这样既满足原版单人世界所有者的优先加载分支，也让
UUID 玩家文件保持正确，兼容后续专用服或非所有者读取路径。

## 实时耐久数据

主客户端运行期间继续按原版区块存盘时机上行区块，但改为请求/确认模式：服务端完成校验并
接受写入后才应答；客户端同区块只保留最新版本，失败时不丢弃待传数据。

每秒在集成服务端主线程获取组内在线玩家 NBT。内容相对上一次已确认版本发生变化时，后台
发送 `PLAYER_DATA_UPLOAD` 并等待物理服完成玩家文件原子替换。该通路确保客户端被强杀时，
物理服务端仍有最近一次已确认的位置、背包、生命值和其他玩家状态，而不只是玩家表中的坐标。

## 两阶段退出事务

退出分为 `保护意图` 和 `最终提交` 两个阶段，事务由随机 `shutdownId` 唯一标识。

### 耐久暂存与提交不变量

`EXIT_PLAYER_DATA` 和 `EXIT_CHUNK_DATA` 只写入
`player-to-player/exit-payloads/<shutdownId>/` 的事务专属暂存区。暂存文件完成校验、原子替换和
`force(true)` 后才确认对象已收到；pending 阶段绝不修改正式 `playerdata` 或 region 存储。

事务状态含义收紧如下：

1. `pending`：只允许继续暂存；强杀后正常重进会丢弃整个暂存目录，正式世界保持最后一次实时确认数据。
2. `committed && !cleanupComplete`：全部暂存对象已齐全，服务端已经耐久承诺必须完成应用。服务端重启、ACK 丢失或客户端改走正常重进时，都必须先幂等应用全部暂存数据，不能 abandon。
3. `cleanupComplete`：正式玩家/区块数据已全部写入并 flush，区块占用与组表已清理。此后才允许删除暂存目录并返回最终 ACK。

应用顺序固定为：持久化 committed 意图 → 幂等写入全部玩家与区块 → flush 全部区块 I/O →
耐久释放注册表占用 → 写入 cleanupComplete → 删除暂存目录。任何步骤失败都保留 committed 和暂存数据，持续重试。

### 第一阶段：保护意图

客户端在暂停菜单 `PauseScreen.onDisconnect()` 的 HEAD 拦截，以保证早于原版
`ClientLevel.disconnect()`；同时拦截其他来源的 `Minecraft.disconnect(Screen)` 和
`Minecraft.stop()`。编排性世界切换不进入该流程。

在原版真正断开本地玩家之前：

1. 组运行时停止接受新地区块申请，并固定当前占用区块清单和在线玩家清单。
2. 客户端向物理服发送 `EXIT_BEGIN`，包含 `shutdownId`、`groupId`、预期玩家和区块清单。
3. 服务端校验发送者是当前主客户端，原子冻结区块并把完整组成员与服务端权威区块清单
   返回给客户端；若物理服刚重启且组表已丢失，只允许同一主客户端恢复自己的玩家状态，
   并验证清单区块没有被其他组占用。
4. 服务端将事务原子持久化到 `player-to-player/exit-transactions/`，再同步持久化冻结后的
   注册表；任一步失败都不返回确认。
5. 只有收到确认后，客户端才调用原版断开，让集成服执行玩家保存、世界保存和停服流程。

服务端断线清理会先查询退出事务。存在未提交事务时，不释放该组区块、不解散组；客户端重连
或服务端重启后仍可继续同一事务。

### 第二阶段：最终提交

退出意图确认后，集成服停服前在服务器主线程捕获全部在线玩家状态和全部已占用加载区块的
最终 NBT。区块找不到实时实例时使用最近一次已确认/已捕获状态，并明确标记“保留服务端已有
数据”，不能用空区块覆盖服务端。

集成服完全停止后，客户端后台执行以下循环，任何一步失败都重新连接并从头幂等重放：

1. 重新发送 `EXIT_BEGIN`，确认事务仍为 pending 或已经 committed。
2. 对每个玩家按 512 KB 分片发送 `EXIT_PLAYER_DATA`；服务端核对总长度与 SHA-256，完整重组
   后耐久写入事务暂存区才确认对象完成。
3. 对每个区块按同样方式发送 `EXIT_CHUNK_DATA`；`preserveExisting` 只有在服务端存储栈实际
   能读取该区块时才确认，不能凭 region 文件存在或客户端声明直接通过。
4. 发送 `EXIT_COMMIT`。
5. 服务端核对本轮已收到全部预期玩家和区块，先把事务标为 committed 并原子落盘，再从
   暂存区幂等应用全部玩家和区块，刷新所有维度的 I/O worker，耐久清理原清单区块与组表并
   写入 `cleanupComplete`；最后才返回确认。

客户端只有收到 committed 确认后，才关闭控制连接、P2P 会话，并在窗口关闭场景继续执行
`Minecraft.stop()`；游戏内退出场景则进入目标界面。

## 幂等与服务端重启

- 相同 `shutdownId`、客户端、组和清单的 `EXIT_BEGIN` 可重复执行。
- 相同玩家或区块数据可重复写入，最终语义是同内容覆盖。
- 服务端重启会从 pending 清单重建并冻结注册表占用；客户端重新发送全部数据，因此无须每个
  区块确认都同步改写事务文件。
- committed 记录另有 `cleanupComplete` 状态。只有尚未清理的 committed 会在重启时补做一次；
  已清理旧事务绝不会再次作用于同一玩家后续建立的新组。
- 相同 `shutdownId` 携带不同客户端、组或清单时拒绝，防止事务 ID 碰撞或篡改。

## 客户端交互与线程模型

退出拦截不阻塞渲染线程。客户端显示原版进度界面，连接和重试在 IO 线程进行：

- 第一阶段确认前，本地世界仍运行，但新区块申请已冻结。
- 第一阶段确认后，客户端主线程只执行一次带旁路标志的原版 disconnect。
- 最终提交在后台重试；窗口关闭请求保持取消状态，直到事务提交。
- 服务器实体和区块序列化只在集成服务端主线程执行。
- NBT 压缩、网络等待、服务端玩家文件写入和事务文件写入在 IO 线程执行。
- 最终 bundle 构建保留固定清单和捕获快照，读取、压缩或发布失败时无限重建；已知区块压缩
  失败不能静默改成 `preserveExisting`。

## 会话代数与实时写入屏障

物理服务端为每个玩家维护当前控制连接身份，并用按玩家条带锁串行“HELLO 替换当前连接”和
“执行权威写入”。旧连接排队的玩家/区块任务只有在执行瞬间仍属于当前会话时才能写入；新
HELLO 必须等待已经开始的旧会话写入结束后才能发布。这样旧任务不能跨会话覆盖新状态。

实时玩家和区块写入还必须与退出 ledger 共用原子许可：先等待同客户端的 `EXIT_BEGIN` 屏障，
再在 ledger 锁内完成“仍未保护”的检查和正式写入。最终事务对象同样在 ledger 锁内完成
“仍为 pending”的检查、暂存写入和 received 标记，commit/abandon 后的迟到数据不得触碰
暂存或正式世界。

实时区块 ACK 必须代表底层 I/O worker 已完成 flush。异常断连按“冻结该组 → 等待该会话全部
已接收写任务 → flush → 耐久释放占用”的顺序执行；失败时保持冻结并后台重试。

## 注册表重启一致性

区块注册表增加只追加、每次确认前 `force(true)` 的变更日志。claim、release、整组释放、
迁移和退出恢复先记录日志再改变内存并应答。每条记录使用版本、载荷长度与 SHA-256 帧，
启动时只允许截断无换行、JSON 未完成或长度/哈希失败的最后一帧；未知版本、未知操作和非法
UUID/区块键必须拒绝启动。单帧硬上限为 64 MiB，防损坏日志在恢复期无限扩容。

全量 checkpoint 的顺序固定为：先向 WAL 追加完整 `replace_all` 状态并 `force(true)`，再写
注册表快照，最后清空 WAL。这样进程无论在快照替换前，还是在快照成功但日志尚未清空时崩溃，
重放末尾都会收敛到同一绝对状态，不会把旧的 `remove_group`/`migrate_group` 重复作用于新快照。
服务端启动时先加载快照再重放日志，因此已经向客户端确认的区块所有权不会丢失一个自动保存周期。

组表丢失后的 EXIT_BEGIN 只能恢复服务端耐久注册表中仍属于该 `groupId` 的精确清单，并重新
执行目标区块及四邻一致性检查。客户端声明不能新增任意未占用区块；服务端耐久注册表本身即
所有权凭证。

## 异常与强杀语义

未取得 `EXIT_BEGIN` 确认就被强杀时，服务端无法区分断电与短暂断网，仍按异常掉线释放占用，
但不会删除或回滚已经确认写入的玩家/区块数据。

已经取得 `EXIT_BEGIN` 确认后被强杀时，服务端先保留事务和占用。该客户端下一次走正常
`ROLE_REQUEST`（而不是退出事务重连）时，服务端判定旧进程已不可恢复：先刷新全部已确认的
实时区块写入，把旧事务标为 `abandoned`，耐久释放原清单占用，再依据最后一次实时玩家数据
指派角色。这样不会永久锁区块，也不会伪造“最终数据已上传”。

## 协议兼容性

新增消息：

- `EXIT_BEGIN`
- `EXIT_PLAYER_DATA`
- `EXIT_CHUNK_DATA`
- `EXIT_COMMIT`

这些消息使用同类型携带 `_rid` 的应答。最终 NBT 分片携带总长度与 SHA-256，服务端重组内存
全局限制为 256 MB。现有 `CHUNK_DATA_UPLOAD` 改为请求/确认语义。
`Protocol.VERSION` 从 2 提升到 3，新旧客户端和服务端不能混用。`MessageType` 编号只新增不修改。

## 测试策略

- 权威玩家状态同时写入 UUID 文件和两个 `Data.Player`，其他 level 数据保持不变。
- 首次加入使用出生状态，再次加入使用上次退出坐标。
- 退出事务开始、重复开始、元数据冲突、重启恢复和已提交 ACK 丢失均保持幂等。
- 服务端未收到全部预期数据时拒绝提交；刷盘、注册表持久化和事务 committed 落盘完成前不应答。
- pending 只写暂存，abandon 删除暂存且不改变正式数据；committed 重启后必须应用暂存，不能 abandon。
- committed/abandoned 后迟到最终数据不执行写入；旧控制连接排队任务不能跨新 HELLO 写入。
- 16–72 MB 的合法退出区块使用退出专用上限，不能被实时单帧上限拒绝。
- bundle 文件读取、区块压缩和 listener 发布失败后保留快照并持续重建。
- 注册表快照落后时通过变更日志恢复已确认 claim；快照已写但 WAL 未清时由 checkpoint 收敛；
  孤儿退出清单不能新增服务端未知区块。
- 客户端连接多次失败后持续重试，重连后从头重放并最终完成。
- 退出意图确认前不执行原版断开；最终提交前不执行窗口关闭。
- 强杀模拟只验证最后一次确认数据仍在服务端，不声称能拦截操作系统强制结束进程。
