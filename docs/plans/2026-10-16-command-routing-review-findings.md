## 1. 严重（critical / important）——已修

| # | 发现 | 处置 |
|---|------|------|
| 1 | **身份判据可被"跨成员拼接"绕过**：`uuid ∈ 组成员 或 名字 ∈ 成员名` 两条分支独立 ⇒ 组内任意成员用"外部 op 的 UUID + 自己的名字"即可让服务端按 op 真实等级执行 3/4 级指令（`/stop`、`/ban`、`/op` 会真实生效） | **已修**：`ConnectionIdentity.canonicalMemberId` 配对判定（UUID 与名字必须同属一个成员），按名字兜底时要求上报 UUID 恰是该名字的**离线派生值**（原版 `ServerLoginPacketListenerImpl` 同款算法）。提交 `0c096bf` |
| 2 | **玩家表一人两行**：位置上报按集成服实体 UUID 落行，而 HELLO 建的是档案 UUID 行（副客户端实体 UUID 是离线派生值）⇒ `/list` 重复计数、`/tp` 约一半概率落到 0,0,0 的幽灵行、`/msg` 随机答"不在线" | **已修**：位置上报归一到成员档案 UUID 后再落行。提交 `0c096bf` |
| 3 | **`/fill` 内部区块漏判**：归属预检只查角点，内部区块不属于任何实参 ⇒ 角点同组、内部他组时执行方主线程永久忙等 | **已修**：按坐标**包围盒**展开（`CommandRouting.Analysis.chunkRange()` + `MAX_ROUTING_CHUNKS=8192` 上限）。提交 `613a472` |
| 4 | **死区块（无主但侧邻属他组）**：认领必然被四邻规则拒（对全网都不可认领），预检却把它当"可申请"⇒ 交回发起组后忙等 | **已修**：`CommandOwnershipRouter.checkExecutableBy` 预演认领条件，命中即拒绝。提交 `0c096bf` |
| 5 | **`contextBound` 形态整体跳过预检**：`/execute positioned … run fill ~ ~ ~ ~45 32 32` 之类"引用执行上下文"的指令只在发起组执行、清单为空 ⇒ 接收端"清单缺省即放行"把两层检查一起短路 | **已修**：相对/局部坐标用**发起者上报的位置与朝向**结算成方块坐标（新增 `yRot`/`xRot` 上报字段），contextBound 分支同样过 `checkExecutableBy` 预演；越界干净拒绝。提交 `0c096bf` |
| 6 | **迟到转发应答触发 ERROR 帧无限回弹**：服务端 request 超时后 pending 已移除，迟到的应答落进"无处理器"分支又回 ERROR（带同一 `_rid`），两端互回不止 | **已修**：`NettyControlConnection` 绝不对 ERROR 帧回 ERROR；服务端对上送形状不符的帧静默忽略。提交 `0c096bf` |
| 7 | **切换窗口的回执被静默丢弃**（合并让出/退出事务：集成服已交出去而玩家还在游戏里，本地执行早已取消 ⇒ 玩家什么都看不到） | **已修**：回执进每玩家有界的暂存队列，玩家重新进入组世界（JOIN）时补投；窗口内 `/tp` 给明确文案。提交 `0c096bf` |
| 8 | **`/forceload add <from>` 被误判为上下文指令**（末节点有未消费的 `to`，被当成"缺省=执行者位置"）⇒ 只落发起组、票据设了但区块加载不出来，仍回原版"Added 1 chunk(s)" | **已修**：区分"缺省参数由同指令**同类型**实参补齐"（to=from）与"取执行者位置"。提交 `0c096bf` |
| 9 | **`/spreadplayers` 的 XZ 中心不计入坐标**（`Vec2Argument` 被判"与位置无关"）⇒ 广播给所有组，各组在别人领地里取样读方块 | **已修**：`Vec2Argument` 纳入位置类（旋转用的是 `RotationArgument`，不受影响） |
| 10 | **维度判据不一致**：预检用客户端自报维度，发起组执行用玩家实时所在维度 ⇒ 谎报维度/穿传送门可绕过预检 | **已修**：发起分支执行前比对"玩家此刻维度 == 上链时自报维度"，不一致即拒绝 |
| 11 | **混版本会重复执行或漏执行**（老客户端+新服务端=发起组执行两次；新客户端+老服务端=发起组漏执行） | **已修**：加性能力位 `commandRouting` 双向声明，服务端只按新语义处理声明过的连接、客户端只在 ACK 看到该位才拦截本地执行 ⇒ 双向安全降级 |
| 12 | **权限名单首次推送必然落空**（客户端在 HELLO_ACK 之后才注册处理器），且被去重签名抑制 ⇒ 本地权限位停在旧值（F3+F4 又不可用） | **已修**：改在客户端已就绪的 `ROLE_REQUEST` 之后清签名强制重推（主线程现算）；签名同时纳入玩家名 |
| 13 | **Netty 线程读非并发 ops 表**（`ServerOpList` 内部是普通 HashMap，与主线程 `/op`、`/deop` 数据竞争，偶发把合法指令判成权限不足） | **已修**：指令上送的权限裁定改读 `PermissionRelay` 在服务器主线程维护的等级快照 |
| 14 | **CHAT_RELAY 无身份校验**（任意已握手连接可以管理员名义跨组发言） | **已修**：与指令上送同口径校验（`canonicalMemberId`） |
| 15 | **成功但执行端无输出时回执为空** ⇒ 玩家端静默，无法区分"已执行"与"被吞掉" | **已修**：补兜底文案"指令已执行（执行端无输出）" |
| 16 | **防冻结链路与落权链路零测试**（预检四分支、`ownedChunks` 复核、名单解析、`_rid` 号段、令牌桶） | **已修**：新增 `CommandOwnershipRouterTest` / `CommandOwnershipVerifyTest` / `LocalPermissionsParseTest` / `TokenBucketTest` / `RidSegmentTest`，`ConnectionIdentityTest` 增配对判据与能力位用例（全量 326 例） |
| 17 | **`.recon/` 与 `test_log/` 未忽略**，在"可自行 commit"的工作流下可能入库 | **已修**：`.gitignore` 加入两项 |
| 18 | **计划文档仍写"CommandsMixin 在 HEAD 取消"**，与最终实现（`client.mixin.CommandDispatchMixin` 注入在 `performCommand` 调用前）不符 | **已修**：`2026-10-15-command-routing-fix-plan.md` 顶部加实施注记，逐条列出偏离与理由 |

## 2. 残余（未修，已记入 `DESIGN.md` §13.2.1）

| # | 残余 | 为什么留 |
|---|------|---------|
| R1 | **控制信道无玩家级认证**（HELLO 的 `clientId` 是自报值）：能连上控制端口者可声称自己是某个 op（会顶掉其在线连接），从而让 `/stop`、`/ban` 在物理服务端真实生效 | 这是"客户端半可信"模型的根，也是 2026-10-15 定稿口径明确记账的取舍；彻底收口需要控制信道的 Mojang 会话校验（独立议题）。**当前部署必须把控制端口按与服务器控制台同权来防护**；本轮把身份判据从"自报即可"收紧到"配对命中本组成员"，但挡不住伪装成 op 的连接本身 |
| R2 | `/spreadplayers` 的**散点半径**（`spreadDistance`/`maxRange ≤ 200 格`）不参与预检 | 只能靠指令名/参数名特判；中心点已计入，中心在自家领地时半径够到邻组属窄窗口。要收口需按参数名特判 |
| R3 | `/place jigsaw` 的**向外延伸**不参与预检（原版该子命令无 `isLoaded` 守卫，其余 `place` 子命令都有） | 延伸范围取决于拼图池与 `maxDepth`，无法从实参统一定界 |

## 3. 判定（经论证不改）

| # | 发现 | 判定理由 |
|---|------|---------|
| D1 | 3/4 级指令（`/stop`、`/ban`、`/op`）会在物理服务端真实生效 | 这是用户 2026-10-15 的定稿口径（决策 3），本轮照此实施并在 `DESIGN.md` §13.2.1 表 4 明确记账 |
| D2 | 选择器只在本组解析（跨组 `@a`/`@p` 语义不完整） | 定稿口径记为范围外（§13.2.1 表 1）；`@s`/`@p`/`@r` 归发起组已覆盖绝大多数玩法 |
| D3 | 集成服专属指令（如 `/publish`）不在物理服指令树里 ⇒ 上链后被判"未知指令" | 指令集以物理服务端为准是设计选择（§13.2.1 表 2）；这类指令极少且不影响玩法 |
| D4 | 隧道接待面不校验对端是否本组成员 | 根因同 R1（自报 clientId 无法作为认证依据）；单独加"按名单校验 clientId"只挡君子，反而给人已加固的错觉 |
| D5 | 落权条目会用 `StoredUserList.add` 把 `ops.json` 写到进程 CWD | 集成服从不读该文件（无回读路径，纯副作用），且只在等级变化时发生（§13.2.1 表 6） |
