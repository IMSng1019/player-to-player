## 0. 目标与不变量

**目标**（按用户实际症状排序）：

1. **服务端 ops 名单里的玩家，在自己所在的组世界里能用该权限级别的指令**（F3+F4 游戏模式切换、`/gamemode`、`/forceload` —— 用户的原话是"导致我客户端无法查看区块整体的情况"）；
2. **全局性指令在全网所有组一致生效**（规范："只有全局性的指令和跨区块的指令需要分级下放"）；
3. 现有链路不退化：跨组 `/tp`、`/list`、`/msg`、聊天分发、副客户端经隧道的路径、退出事务与区块写回。

**不变量（动代码时必须守住）**：

- `GroupHost.java:183` 的注释是**有意决策**："不开放作弊，组世界的权威演算不应被本地作弊指令干预"。因此**不要**改成 `allowCheatsForAllPlayers(true)`、**也不要**改 `level.dat` 的 `allowCommands`——权限必须**按玩家、按服务端 ops 名单**精确授予。
- **阶段 A 与阶段 B 必须同一个变更集落地**（复查新增的硬约束）：只修 A（本地权限）会让全局指令从"只落他组"变成"只落本地"，多组一致性反而更差；只修 B 则本地特权指令依旧哑火。两条验收要一起写。
- **阶段 A0（玩家表落库 + 身份绑定）必须与 A 同批**：今天的跨组 `/tp`、`/msg` 依赖玩家表，而表恒空（G-09）；且一旦表开始有数据，位置上报的自报 uuid 就会变成可用的注入面。
- **身份绑定是 P0 前置（2026-10-15 决策 3 的后果）**：3/4 级指令改为**在服务端真实执行**（`/stop`、`/ban`、`/op` 会生效）⇒ 若不先把 `playerUuid/playerName` 与连接绑定，任何已握手客户端都能冒用 op 身份停服/封人。这条不能推迟。
- **不要动** `forwardToOtherPrimaries` 的权限钳制（2）与"发起组不回灌"的既有意图；B 阶段要改的是**触发轴**（类别判定）与**幂等边界**，不是把范围放大。
- 跨组转发的权限继续钳到 2（`CommandChatHandlers.FORWARD_PERMISSION_CAP`）：`/stop`、`/op`、`/ban` 这类 3/4 级指令绝不跨组执行（防一台机器的管理员关停别人的集成服务端）。
- `WorldIdentity` 只吃 `WorldGenSettings`（`WorldIdentity.java:200-219`）——改 `level.dat` 的开关不进身份哈希，但会进**环境骨架**，所以仍然不动它。
- 协议只做**加性字段**，不升 `Protocol.VERSION`。

## 2. 方案

### 阶段 A0（P1 前置，必须与 A、D1 **同批**落地）：玩家表落库 + 身份绑定

**为什么前置**：复查 G-09 已核实——**玩家表从未被写入**（`PlayerTable.put` 无调用者），所以 `/list`、`/tp <玩家名>`、`/msg` 三个特例今天全是死代码，1Hz 位置上报是空转；**只修 A 而不修 A0，验收里的"跨组 /tp、/msg 不退化"根本无从谈起**（它们本来就不可用）。同时：**修好 G-09 会激活今天完全惰性的坐标注入面**（`RegistryHandlers.java:336` 用消息自报的 `uuid` 调 `updatePosition`），所以**身份绑定必须与它同批**，否则"修复本身"就是新攻击面的开关。

- **A0-1 落库**：在哪登记？优先用**物理服务端自己的权威信息**（玩家加入/角色指派时由服务端登记 profile），而不是采信客户端 JSON；坐标仍由 1Hz 上报填充，但接收端从 `computeIfPresent` 改成"**仅对已登记且属于上报连接所在组的玩家**"生效（`ServerPlayer` 概念：位置权威在客户端、成员资格权威在服务端）。
- **A0-2 身份绑定**：`PLAYER_POS_UPDATE` / `COMMAND_RELAY` 的 `uuid` 只接受**该连接所在组的成员**（以 `conn.peerId` → `GroupTable` 反查）。**不要高估**：它只保证"同一连接自洽"，挡不住同组内冒用 op 的 uuid（那需要改信任模型，见 §4 决策点 5）。
- **A0-3 玩家表消费面同时修边界**：`/list`（G-04：进"仅上送"类别或改文档）、`/msg` 文本提取（G-08，改 Brigadier 取参）、`/tp` 落点新鲜度（G-07，可选）。
- **A0-4 验收**：两个客户端在同一组时 `/list` 能列出**全网**玩家；`/tp <他组玩家名>` 走 `action=teleport` 生效；`/msg <他组玩家>` 投递正确；**他人无法用别人的 uuid 刷位置**（负例测试）。

### 阶段 A（P0，最小可用）：服务端权威权限下传 + 本地精确落权

**A1 服务端下发**（加性协议字段）

- `HelloHandler` 的 `HELLO_ACK` 增加 `permissionLevel`（int，已按口径钳制）；取值来源 `MinecraftServer.getProfilePermissions(profile)`（与 `CommandChatHandlers.java:106-107` 同一权威口径）。
- **变更推送**：ops 名单变动极少，第一版用**低频轮询 + 顺带回填**即可——① 玩家每次进服（HELLO 握手）下发一次；② 服务端侧每 5 秒对在线玩家做一次 diff，变化则推；③ 收到该玩家 `COMMAND_RELAY` 应答时顺带带上最新值。三条任选其一即可满足"服务端 /op 之后客户端立刻能用"。
- 不新增复杂帧：优先复用 `HELLO_ACK` + 一条轻量 `PERMISSION_RELAY`（服务端→客户端单向，只在变化时发）。

**A2 客户端落权**（只在**被接管**的集成服上做）—— 注入点已由校验代理 javap 复核，按此实施：

1. **唯一推荐路径（已核实 public）**：`server.getPlayerList().getOps().add(new ServerOpListEntry(profile, 目标等级, false))` + `server.getPlayerList().sendPlayerPermissionLevel(player)`；
   - **不要用** `PlayerList.op(profile)`：它内部用 `getOperatorUserPermissionLevel()` 建条目，**等级不可控**；
   - **目标等级 = 服务端 ops 名单核出的真实等级**（2026-10-15 用户定稿，不钳制）——F3+F4、指令补全、以及未拦截路径都按真实等级生效。
   - **注意区分**：**组间广播执行的权限**仍保持 `FORWARD_PERMISSION_CAP = 2`（`CommandChatHandlers.java:63-64`）——两者作用面不同：本地权限位决定"这台客户端本地能看到/能做什么"，广播权限决定"这条指令在别的组世界里能以什么等级执行"；对本模型里会广播的 0–2 级指令，两者取值差异不影响成败。**≥3 级指令不进广播**（决策 3：只在服务端执行）。
2. ❌ **候选 3（直接设 `ServerPlayer` 权限）不可行**：`ServerPlayer` 没有权限 setter，`getPermissionLevel` **每次实时派生**自 `MinecraftServer.getProfilePermissions` ⇒ 设不了（最多伪造客户端显示态）。
3. ❌ 候选 2（mixin accessor）**无必要**（`getOps()` 已 public）—— 作废。
- **生命周期与线程**：必须在**集成服主线程**上做（`ServerOpList` 内部是 `Maps.newHashMap`，非并发 map）；`GroupRuntime.arm` 时清一次旧值、收到新值覆盖；拆除时移除。**注意拆除路径不止 `disarm`**（`disarm` 是启动失败回退；正常拆除走 `detach`）——两处都要清，别留跨世界残留。
- **持久性（更正我原来的说法）**：这是**纯进程内、按会话**的落权——集成服不读 `ops.json`（见 §5），所以**没有持久化，也没有崩溃残留问题**；每次进服由 A1 重新下发。
- **覆盖面（校验补的缺口）**：A1/A2 默认只覆盖**发起连接的那一个玩家**；**副客户端被 `/op` 后组内仍不可用**（它的指令是在宿主集成服上执行的，而宿主的名单里没有它）。⇒ A1 应下发**该组成员 → 权限**的映射（或按成员逐条下发），A2 在宿主侧给组内每个成员都落一条。

2'. **上限**：与转发口径一致（默认 2，见 §4 决策点 1）。

**A3 预期效果**

- 本地合理指令在本地成功 → 上送链路只承载"本地根本不存在（未知命令）"与"跨组"两类指令，恢复规范"只有全局/跨区块才分级下放"的本意；
- F3+F4、`/gamemode spectator`、`/forceload` 立即可用（用户的原始诉求："查看区块整体情况"）；
- **指令树/补全恢复**：原版按权限过滤下发给玩家的指令树（`IntegratedServer.publishServer` 末尾 `Commands.sendCommands(player)`，已 javap 核实）——权限 0 时 OP 指令**连补全都看不到**；落权后应立刻可见（可当验收判据）；
- 服务端日志里"指令上送"只在真正跨组时出现（可当验收判据）。

**A4 测试**

- 单测：权限计算与钳制（0/1/2/3/4 → 0/1/2/2/2）、`HELLO_ACK` 字段序列化兼容（老客户端无字段 → 权限 0，行为不变）；
- 集成：本地玩家权限=2 时 `/gamemode creative` 成功且**不**上送；权限=0 时行为与现在一致；
- 手工验收见 §6。

### 阶段 B（P1）：全局指令的分级下放（发起组也参与，且恰好执行一次）

- **B1 分类表**（客户端/服务端共用同一常量类，新增 `group/CommandRouting.java`）：全局指令前缀白名单**只放幂等的世界状态类** —— `time`、`weather`、`gamerule`、`difficulty`、`save-all`、`save-off`、`save-on`（明确列全，不做推断）。
- **B2 客户端**：命中白名单的指令 —— **本地执行一次**（发起组的效果）**再**上送一条带 `broadcast=true` 的请求；语义="只发给其他组"。
- **B3 服务端**：`broadcast=true` 时走现有 `forwardToOtherPrimaries`（它已经是"广播给全部其他组"），把汇总结果回给发起端：`handled=true` + "已在 N 个组生效"/"其他组未生效"；**发起组不回灌**（本地已执行）→ 每个组恰好一次。
- **B4 取舍与边界**：非幂等指令（`give`/`summon`/`fill`/`xp`…）**不入白名单**；白名单由单测锁住，防误加。
- **B5 顺带收口两件事**（都在同一张分类表里表达，成本极低）：
  - **`/list`**：把 `list` 放进"**仅上送**"类别（客户端命中后**不上送失败路径而是无条件上送**，服务端特例应答全网名单）——否则服务端那条特例永远是死代码、`DESIGN.md:483` 的声明永远为假。若不想动，则**改文档**承认"本组视野"（二选一，别留悬空）。
  - **3/4 级指令（`/save-all` `/stop` `/op` `/ban`…）**：**显式写进"不支持清单"**（DESIGN + 玩家可见提示），理由=权限钳到 2 的安全取舍（`CommandChatHandlers.java:41-44` 已文档化）。不要留"看起来该能用其实永远不能用"的状态。
- **B6 测试**：分类表单测；两组夹具下"发起组 + 另一组"都生效；`/give @p` 这类**不得**出现在他组的"已代执行"日志里（对应 G-02 的否证用例）；另一组全失败时只提示"其他组未生效"，不重复本地报错。

### 阶段 C（P2，可选，与 B 同会话做或排后）

- **C1 报错时序**：与规范**等效**（本地报错即最终答复），建议只在 `DESIGN.md` §13.2 记为有意偏离，**不改代码**。
- **C2 选择器跨组**（`@a`/`@p`）：明确记为**范围外**，在 DESIGN 写清"选择器只在本组解析"的边界；将来要做就走 B 的同一条路（广播 + 各组本地解析 + 幂等约束）。
- **C3 幽灵下线**：客户端"编排性断开"时主动关闭物理连接（或服务端识别切换原因换用准确文案），消掉"我还在线服务端却报我离开"的误导日志（30 秒 keepalive 超时，见 `2026-10-14-stale-p2p-state-after-world-replace.md` §7.5）。与指令语义无关，但同一批日志噪音。

### 阶段 D（P2，安全收口，可独立做）

- **D1 身份绑定**（复查 G-06）：`COMMAND_RELAY` / `PLAYER_POS_UPDATE` 的 `playerUuid` 目前是**客户端自报**（`CommandChatHandlers.java:92-94`、`RegistryHandlers.java:335-347`），可直接冒用 op 的 UUID 换取 permission=2。二选一：① 明文接受"客户端半可信"并写进 DESIGN；② 加一层绑定——用 `conn.peerId` 反查该连接的组，只接受**该组成员**的 uuid（玩家表成员资格核对）。**建议 ②**（成本低：两处入口各加一次成员校验；对照：区块探测路径本来就有 `withCurrentSession` 会话核验）。
- **D2 `/msg` 文本提取**（复查 G-08）：`CommandChatHandlers.java:140` 用 `command.indexOf(tokens[1])` 定位正文，玩家名与指令字面量同形时截错（`/msg tell hi`）。改成按 Brigadier 解析结果取剩余参数。

## 附录 P：全量上链 + 广播执行 —— **用户 2026-10-15 拍板口径（定稿）**

> **决策记录**：用户明确选择"**所有指令一律上链 → 服务端按 ops 名单校验 → 广播给所有组客户端（含发起组）各执行一次**"，并给出理由：
> ① 统一，不必再区分"全局性/跨区块"（不需要维护白名单）；
> ② 指令的本意就是"对所有组各执行一次"，不局限于当时的组；
> ③ 兜底依据=规范那句"**在原版中不合理的指令是不会被执行的**"——看似重复的指令会有报错存在来兜底（目标名字不在该组的那些组会报错、什么也不做）。
> **本附录按此口径推进**；下文的"按目标解析落点"（P.1）**降级为备选**（若将来发现广播的错位面不可接受，可平滑切回——两者共用同一套服务端裁定与接收端执行面）。

**目标**：指令的**权限裁定唯一在物理服务端**；客户端不再自己判断"我能不能执行"；一条指令的语义 = **在所有组各执行一次**。

> 与规范的关系：L48"传输的顺序是副客户端→主客户端→中转服务端→服务端"、"在指令被传递完所有的端都报错后则返回本地的报错信息"——**P 比现行实现更贴字面**；现行实现是"本地成功即终止"（`CommandRelayClient.java:167-174`）且**发起组被排除**（`:190-193`）。

**流程（按用户口径定稿）**

1. 任一客户端（主/副）输入指令 → **无条件上链**，并由 `CommandsMixin` 在 HEAD **取消本地执行**（避免发起组执行两次）。
2. 服务端：`perm = min(getProfilePermissions(profile), CAP)`；`perm` 不足该指令所需等级 → 直接应答失败文案；否则**广播给所有组（含发起组）各执行一次**。
3. 各组主客户端在本地以 perm 执行一次；发起组用**发起玩家实体**当指令源（`@p`/`~`/`@s` 的语义在此组保持原版），其他组的锚点按审计结论定。

| 类别 | 服务端动作 | 说明 |
|---|---|---|
| **全部玩家指令** | 广播给所有组（含发起组）各执行一次 | 用户口径：一条指令的语义 = 全网各执行一次 |
| 目标不在该组的那些组 | （无需特判）该组执行时报错、什么也不做 | 兜底依据=规范"在原版中不合理的指令是不会被执行的" |
| 无权限 / 解析失败 | 应答 `handled=false` + 文案 | 规范"所有端都报错后返回本地报错" |
| `/tp <他组玩家>` 类 | 规范点名的那条例外：作用对象是发起者、落点在他组 | 需要玩家表解析（A0）——广播解决不了这类 |

3. **报错时机随之改变**：本地不再即时报错（因为本地不执行），改为服务端回执后显示——更贴规范，代价是每条指令一次 RTT。

**需要新增/改动**：客户端探针语义反转（无条件上链 + 抑制本地执行，`/execute` 等复合形态需单独定界）；服务端新增"本地域授权"分支 + 全局广播 + 权限回执字段；客户端新增"授权回放"（玩家实体源 + 指定权限）；**A0（玩家表 + 身份绑定）仍是前置**。

### P.0 审计结论（6 代理：3 审计 + 2 对抗校验 + 1 草案，2026-10-15）

**用户的"兜底论据"成立，而且比预想的更硬——三层机制（均已字节码/代码核实）**：

1. 目标名字不在该组 → 该组报错、无副作用（`/gamemode c Bob`、`/msg Bob`、`/ban Bob` 等）；
2. **方块类指令由"区块归属门控"挡**：远距无票区块 → `hasChunkAt` 为假 → `getLoadedBlockPos` 抛 `argument.pos.unloaded` → 只有真正持有该区块的组落笔一次，**不会重复**（这是"看似重复有报错兜底"在方块类指令上的具体机制）；
3. 权限 >2 / 仅服务端 / 仅 IDE 的指令在各组根本不存在或无权限 → 齐声报错。

**⚠️ 但兜底有一个"反转的洞"（对抗校验 CONFIRMED，P0）**：**有票但被该组拒绝的区块**（玩家视野内或 `forceload` 过、holder 在、票级 ≤31）会让加载检查**通过** → `getOrScheduleFuture` 悬置 → `ServerChunkCache` 的 `managedBlock + join()` **把该组主线程永久停等**（集成服**没有 watchdog** ⇒ 不是崩溃而是永久冻结）。可达路径不止 `/fill` 跨区：`/setblock` 边界、`/execute if/unless block`、`/item`/`/loot` 写入、任何在一次 `/forceload` 之后触块的指令；另有 `ChunkMap.save → readChunk().join()` 同源风险。**广播会把这类执行从"偶发"变成"每条触块指令 × 每个非持有组"**——所以实现时必须配一条守则（三选一，见下）。

**其余残留三类（对抗校验 CONFIRMED）**：

| 类别 | 例 | 广播后果 |
|---|---|---|
| **源上下文选择器** | `/give @p diamond`、`/effect give @r …` | `@p`/`@r` 只靠"源位置"解析 ⇒ 每组各选中自家出生点附近一名玩家，**不报错、静默 N 份**（仅当发起者是 op 时才发生；非 op 会先被 `ERROR_SELECTORS_NOT_ALLOWED` 挡下） |
| **相对坐标/缺省位置** | `/setblock ~ ~-1 ~ stone`、`/particle …`、`/summon zombie` | `~` 以**各组出生点**为原点 ⇒ 静默落在各组出生点 |
| **自指形式** | 裸 `/kill`、裸 `/clear`、裸 `/gamemode creative`、`/tp x y z`、`/effect clear` | 虚拟源 `entity=null` ⇒ `@s`/自指一律报"未找到实体/玩家" ⇒ **功能缺失**（安全但不可用） |

**规范的 tp 例外仍不可少**：`/tp <玩家>`、`/tp <坐标>` 作用对象是发起者、落点在他组，任何组都完不成 ⇒ 必须由服务端按玩家表解析回传（现有特例）。

**一条"形状规则"可同时消灭后三类（不引入任何指令名白名单）**：**凡引用了"执行上下文"的指令（`@s`/`@p`/`@r`/`~`/`^`/缺省位置）→ 只在发起组执行，且用【发起玩家实体】当指令源；其余 → 所有组各执行一次。** 判定从**解析树**自动得出（是否引用源实体/源位置），不是维护列表——符合用户"不用区分全局/非全局"的诉求，同时让 `/give @p`、`/kill`、`/clear` 等恢复原版语义。

**挂死守则（三选一，需拍板）**：
1. **归属预检（推荐）**：服务端从解析树取出方块/坐标参数 → 查区块注册表 → **只把指令发给持有这些区块的组**，非持有组直接跳过（顺带消灭错位执行）；
2. **不广播"触块类"指令**（只广播不触块的形态）；
3. **让门控快速失败**：被拒的区块加载 future 以异常完成（把"永久挂死"变成"原版报错兜底"）——最贴用户的兜底论据，但改动模组核心门控语义，需单独评审 + 实测。

**实现层三个必修前置（草案给出，均已核实）**：
- **_rid 号段隔离**：新设计下"服务端→发起组下发 execute"与"发起组→服务端上送"在**同一条连接**上并存，且两者 MessageType 都是 `COMMAND_RELAY`，`NettyControlConnection` 只按数字匹配 `_rid` ⇒ 会互吞/错帧完成（稳定可复现）⇒ 必须按连接角色分号段；
- **身份绑定**（G-06 升级为前置）：全量上链后服务端 ops 判定成为**唯一**权限边界，而 `playerUuid/playerName` 仍是 JSON 自报 ⇒ 必须绑定；
- **超时/断连兜底**：本地执行被取消后，RTT 期间连接死亡或 15s 超时 = 指令消失且无原版报错 ⇒ 需定义（建议：超时报错；**不要**回退本地执行，否则与广播执行竞态）。

**拦截入口建议（草案）**：不要改 `CommandsMixin`，改在 **`ServerGamePacketListenerImpl.performChatCommand` 的 HEAD（cancellable）** 注入——精确对应"玩家发指令"，天然排除告示牌/命令方块/数据包函数/第三方程序化调用；聊天栏与 F3+F4 都经此入口。数据包函数**不存在**"本地照跑+上链一次"的双重执行（它们从不经过该入口，玩家打的 `/function` 作为一个整体被拦截一次）。

### P.1 落点规则：按**目标解析**而不是按"指令名白名单"（**备选**；用户已选 P 全量广播）

用户要求"不用再区分哪些是全局、哪些是非全局"。可行的统一口径是把分类从**指令名表**移到**目标解析**（服务端用玩家表 + 解析树做）：

| 该指令的目标形态 | 落点 | 理由 |
|---|---|---|
| 目标 = 发起者本人 / 本组成员 / 相对坐标（`~`）/ 无显式跨组目标 | **回发起组执行一次**（上下文 = **发起玩家实体**，不是 `entity=null` 虚拟源） | 选择器与相对坐标天然指向发起者所在世界 = 原版语义 |
| 目标是**其他组的玩家**（显式名字或选择器命中他组成员） | **只路由到拥有该目标的组**（可多个）执行一次 | 规范"服务端可以执行原主客户端不能执行的 tp 指令"的推广 |
| **完全没有实体/坐标参数**（`time`/`weather`/`gamerule`/`difficulty`/`save-*`） | **广播给所有组各执行一次** | 世界状态类；每组一次 = 全网一致 |
| 其余 / 解析失败 | 服务端应答报文（`handled=false` + 文案） | 规范"所有端都报错后返回本地报错" |

- 好处：**不需要维护"全局指令白名单"**（分类由参数形态得出），也不会让本地效果乘倍；
- 仍需固化的少数例外（各自已有或需新增特例，不属"白名单"维护）：`/list`（服务端直接应答）、`/msg|tell|w`（私聊投递）；3/4 级指令（`/save-all` 等）本来就被权限钳制挡在门外；`/say`/`/me` 无参 → 广播 → **每组各说一次**，恰好等于"全网都看到"；
- 已知限制（必须写进 DESIGN）：**数据包函数内部的指令不走 `Commands.performCommand`**（`CommandsMixin` 拦不到）⇒ 在 P 下会出现"本地照跑 + 上链一次"的双重执行，需要在方案里明确（限制 `function` 上链或接受）。

**⚠️ P 单独不能解决的两件事（已 javap 核实）**：

- **F3+F4**：客户端 `KeyboardHandler` 在发指令**之前**就用 `player.hasPermissions(2)` 拦截（和聊天栏不同，聊天栏无条件发包）。要么额外 mixin `KeyboardHandler`（把 F3+F4 也改成"上链请求切模式"），要么仍然给本地玩家一个 ≥2 的权限位。
- **指令补全**：`Commands.sendCommands` 按权限过滤下发给客户端的**指令树**——补全里要能看到 `/gamemode`，本地权限位必须 ≥2。

**代价/风险**：每条指令一次 RTT（本地指令也变慢）；本地游玩对物理服务端+中继形成**硬依赖**；对**本地域**指令而言服务端裁定**无法强制**（客户端拥有本地世界，改客户端即可绕过）——所以它是**权限模型**的选择，**不是安全边界**；真正的安全边界只在**跨组效果**上（那一侧服务端本来就中介）。

**与"权威缓存+例外上链"（主方案 Q）的关系**：Q = P 的裁定结果**缓存**到客户端（A1），本地域指令本地**立即**执行、不再逐条上链；跨组/全局仍走 P 的分支。两者共用 A0、共用全局广播与跨组特例，差别只在"本地域指令是否逐条上链"。
