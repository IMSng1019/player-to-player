# 进组世界时错误触发耐久退出的修复

## 现场证据与根因

依据 `test_log/26.10.31_3` 及该日志指向的本机隔离客户端、计算进程日志：

- 原游戏目录的两份客户端日志分别在 18:53:50、18:56:05 自动环境重启时结束，并未覆盖故障时刻。
- 隔离客户端在 18:54:29、18:56:41 均已取得 worker READY，随后开始从物理服切换到本机游戏桥。
- 两次切换中，Netty 线程先报告“世界切换中的编排性断开”，随后立即出现 `client-exit` 耐久退出事务。第一次还完成了本地 JOIN 后才收到服务器关闭；第二次在本地 JOIN 前已经关闭。
- 因此此次灰屏、仅显示物品栏以及第二次无法进入，来自正常连接切换误启动退出屏障，导致刚启动的计算进程被冻结并停止。

本地 Minecraft 1.20.4 字节码及 Fabric Networking 3.1.9 源码确认：
`ClientLevel.disconnect()` 关闭网络 channel 时，Fabric 在 Netty 线程发出 DISCONNECT；
旧 `WorldSession.onLeave` 消费全局布尔旗标，提前撤销了退出拦截器使用的保护。
随后显式 `Minecraft.disconnect()`，以及 `ConnectScreen.startConnecting()` 内部无条件再次
调用的 `disconnect()`，都可能把 worker 已就绪的状态误判为主动退出。

## 实现

- 用 `ConnectionSwitchGuard` 将调用线程的同步切换作用域与具体旧连接的单次断开事件分开。
- 作用域覆盖关闭旧游戏连接、清理客户端世界以及原版开始连接入口的全部同步调用，始终在 `finally` 中释放。
- Fabric 事件按连接对象身份消费，晚到旧事件不会吞掉新连接退出；会话结束时清理未消费引用。
- 锁只保护事件许可集合，不在锁内执行网络关闭，避免渲染线程等待 Netty 回调时互相阻塞。
- 初次进组、主副切换及分离等待使用同一入口。真正主动退出与关闭游戏仍经过原有耐久屏障。

遵循提示词中的客户端承担演算、唯一组归属及持久化退出约束。本次不改变控制协议、
消息类型、Mixin 声明、Fabric 元数据或配置格式。
